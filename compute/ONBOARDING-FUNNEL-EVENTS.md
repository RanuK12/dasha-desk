# Provider onboarding funnel — event taxonomy

**Status:** spec only — no implementation.  
**Audience:** whoever implements analytics (Worker team for server-side events, compute/ maintainers for installer-side events).  
**Context:** live Mac supply is Dasha Compute's binding constraint. The funnel tells us *where* prospective providers drop and *why*, so fixes target the real bottleneck instead of the loudest complaint.

## Funnel stages (happy path)

```
register → download → token_saved → install_started → doctor_passed
→ key_stored → benchmark_run → service_started → first_heartbeat
→ first_job_assigned → first_job_completed → active_7d → active_30d
```

## Event envelope

Every event carries the same envelope; payloads below are additive.

| Field | Type | Notes |
|---|---|---|
| `event` | string | one of the names below |
| `provider_id` | string | the provider id (NOT the token); empty string before registration |
| `install_id` | string (uuid) | generated by install.sh per attempt; joins events across one install run |
| `occurred_at` | string (ISO-8601 UTC) | client clock is fine; server stamps its own on ingest |
| `app_version` | string | kit version, e.g. `0.3` |
| `os` | string | e.g. `darwin-arm64`, `darwin-x86_64` |
| `chip` | string | e.g. `apple-m4`, `apple-m1`, empty if undetected |
| `memory_gb` | number | unified memory, empty if undetected |
| `ollama_version` | string | empty until known |
| `coordinator` | enum | `live` \| `local` — which endpoint the provider points at |

Privacy rules (non-negotiable): **never** send `DASHA_PROVIDER_KEY`, Keychain contents, shell history, or prompt/job text. `provider_id` is the only stable identifier.

## Event definitions

### Web side (www/compute — Worker boundary; the Worker team owns these)

**`registration_started`**
- Payload: `{ referrer: "compute-provide" | "ocm" | "direct" }`
- Answers: how many people open the Provide flow?

**`registration_completed`**
- Payload: `{ model_map_default: "qwen3-8b=qwen3:8b,…", mlx_capable: bool }` — `mlx_capable` from client UA/heuristics where available.
- Answers: how many get a token? What default model map do they accept?

**`kit_download_started` / `kit_download_completed`**
- Payload: `{ bytes_total: number }` (completed only).
- Answers: does the tarball download finish? (Abandoned downloads = CDN/ISP issue, not installer UX.)

### Installer side (compute/ — emitted by install.sh / agent.py; transport TBD by Worker team, e.g. a lightweight ingest endpoint)

**`token_saved`**
- When: `provider/save-provider-key.py` writes the 0600 token file successfully.
- Payload: `{}` (envelope only).
- Answers: do people complete the hidden-input token step, or bail at the prompt?

**`install_started`**
- When: install.sh passes env validation and invokes doctor.
- Payload: `{ reinstall: bool }` — reinstall detected via existing `$APP_DIR/provider.env`.
- Answers: how many validated setups actually begin installing? (Gap vs `token_saved` = validation friction: bad provider ids, malformed model maps.)

**`doctor_run`**
- When: `agent.py --doctor` exits, pre-install and on every manual `dasha-compute doctor`.
- Payload: `{ exit_code: number, failing_checks: ["disk","key",…], warnings: ["memory",…], context: "pre-install" | "manual" }`
- Answers: **which checks kill installs?** Ranked `failing_checks` is the single most valuable table in this spec.

**`doctor_passed`**
- When: `doctor_run` with `exit_code == 0`, pre-install context.
- Payload: `{ warnings: ["memory",…] }`
- Answers: pass rate of first-time installs; warnings that later correlate with churn (see analysis below).

**`models_pulled`**
- When: all missing mapped models are present after the install-time pull step (or when a later `ollama pull` completes the set — see `model_added`).
- Payload: `{ models: ["qwen3:8b",…], bytes_downloaded: number, duration_s: number }`
- Answers: pull failure / slowness as a drop cause; bytes per install for CDN cost.

**`key_stored`**
- When: `security add-generic-password` succeeds and the token file is deleted.
- Payload: `{}`.
- Answers: Keychain/TCC friction rate. (If this fails, the token file survives and the user can retry — count retries via `install_id`.)

**`benchmark_run`**
- When: install-time `agent.py --benchmark` completes.
- Payload: `{ results: [{ model: "qwen3-8b", tokens_per_second: number, eval_seconds: number }] }`
- Answers: real throughput distribution across the fleet; seeds the supply-quality model (slow Macs → small models only).

**`service_started`**
- When: `launchctl bootstrap` + `kickstart` succeed.
- Payload: `{}`.
- Answers: install completion. The funnel conversion headline is `service_started / registration_completed`.

**`first_heartbeat`**
- When: the provider's first successful poll reaches the coordinator.
- Payload: `{ poll_latency_ms: number }`
- Answers: does the service actually run after install? (Gap vs `service_started` = launchd/KeepAlive issues, token read failures at startup.)

**`first_job_assigned`**
- When: coordinator assigns the provider its first job.
- Payload: `{ model: string, prompt_tokens_est: number }`

**`first_job_completed`**
- When: the first job returns a terminal result (done or provider-reported error).
- Payload: `{ model: string, success: bool, tokens: number, duration_s: number, error_class: string | null }`
- Answers: time-to-first-success; error classes that strand new providers (OOM, Ollama crash, timeout).

**`model_added`**
- When: a mapped model becomes installed that wasn't at install time (detected via heartbeat model inventory diff).
- Payload: `{ model: string }`
- Answers: upsell effectiveness of the model catalog.

**`provider_active_7d` / `provider_active_30d`**
- When: server-side, on the 7th / 30th day with ≥1 completed job in the trailing window (7d: any 1 job; 30d: jobs on ≥4 distinct days).
- Payload: `{ jobs_completed: number, tokens_served: number }`
- Answers: retention. 30-day-active providers are the supply metric that matters.

**`provider_paused`** (server-side: no heartbeat for 72h) / **`provider_uninstalled`**
- Payload (uninstalled): `{ via: "dasha-compute uninstall" | "keychain_delete" | "inferred" }`
- Answers: churn reasons; pair with the last `doctor_run` warnings to find predictors.

## Funnel-drop questions each event answers

| Question | Events that answer it |
|---|---|
| Where does the funnel leak worst? | sequential conversion: `registration_completed → install_started → service_started → first_job_completed → active_30d` |
| Is doctor the blocker or the savior? | `doctor_run.failing_checks` ranked; correlate with `install_started` retries per `install_id` |
| Which Macs should we even target? | `doctor_passed` + `benchmark_run.tokens_per_second` joined on `chip`/`memory_gb` → minimum viable hardware |
| Do warnings predict churn? | `doctor_passed.warnings` vs `provider_paused` within 14d |
| Is the token step confusing? | `registration_completed → token_saved` gap; `install_started` validation failures |
| Are model pulls too heavy? | `models_pulled.duration_s` / `bytes_downloaded` vs drop between `doctor_passed` and `key_stored` |
| Does first-job success predict retention? | `first_job_completed.success` vs `active_7d` rate |
| How much supply is MLX-capable? | `chip`/`memory_gb` distribution at `registration_completed` vs `service_started` (are M-series owners converting?) |

## Implementation contract for the Worker team

1. **Ingest endpoint** (new, server-side): `POST /v1/analytics/funnel` accepting the envelope above; unauthenticated but rate-limited per IP; validates `event` against this taxonomy and drops unknown fields silently (forward-compatible).
2. **Server-side events** (`first_heartbeat`, `first_job_*`, `active_*`, `provider_paused`) are derived from existing coordinator state — no provider changes needed.
3. **Installer-side events** need a tiny emitter in install.sh/agent.py (curl to the ingest endpoint, best-effort, 3s timeout, never blocks install on failure). Emitting must never include the provider key.
4. **Dashboards, v1:** (a) funnel conversion by stage; (b) `doctor_run.failing_checks` ranking; (c) throughput histogram by chip from `benchmark_run`; (d) 7d/30d retention curve. Anything fancier is v2.
5. Keep the taxonomy append-only: new events get new names; never repurpose a payload field.
